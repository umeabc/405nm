# 405nm 路线图（M1 → v1 上线）

## 一、v1 的验收标准

**一条完整链路端到端跑通**：

```
图源入库 → 翻译 → 校对 → 导出嵌字包 → PS 嵌字 → 回传成品 → 一键导出发布包 → 定时发到 B 站
```

不是「每个模块都能用」，而是**这条链路上的每一环都不需要人工搬数据**（不靠下载文件、改文件名、手动传图）。任何一环需要有人「手工补一下」，都算没打通。

配套要求：
- 现有彩翻的用户能无损迁移过来（含图片与署名），且**迁移可重跑、可验证**。
- 与既有生产环境并存部署，不触碰同机上的其他服务。
- 组内日常最依赖的环节（翻校）在 v1 就必须是**可生产使用**的，不是演示级。

## 三、逐里程碑详情

### M1 身份与团队 ✅

**目标**：所有后续功能都挂在这套身份与权限上，所以它必须先立稳。

**交付**
- 用户、团队、团队成员；邀请码绑团注册（一码绑一团队、多用途、可停用、自动入团）。
- 角色与权限：权限码落**关联表**（而非位掩码），可查询可审计；团队角色 5 个（创建人/管理员/资深/成员/见习）。
- 站点后台：用户管理、团队概览、站点设置、公告。
- 权限分两层：**团队级**与**作品级**各走各的校验。

**关键决策**
- 会话用**数据库不透明令牌**而不是 JWT —— 改密码 / 移出团队必须能立即失效，JWT 做不到。
- 密码 scrypt；登录失败次数限流（成功即清零）；注册按 IP + 全站双窗口限流。
- 权限码用点分字符串并**保留与旧站枚举码的对应关系**，供迁移时逐一映射而不是猜。

**验收**：能建团队、发邀请码、按角色看到不同入口；40 项断言通过。

---

### M2 项目与文件 ✅

**目标**：把「作品」这个概念立起来 —— 之后翻校、图源、导出才有挂靠的地方。

**交付**
- 作品集 / 作品 / 文件 / 目标语言；作品内角色（建作品时从团队模板实例化）。
- 作品编号（团队内自增，`UPDATE ... RETURNING` 原子分配）。
- 存储抽象（v1 只 local 驱动）；缩略图 520px / 预览图 2000px。
- **媒体字节流服务**：图片经应用鉴权后流式吐出，不放 nginx 静态目录。
- 团队级 MD5 去重；自然排序键（数字段左补零到 12 位，数据库排序即自然序）。
- Comiku 风格工作台：作品卡 + 状态 chips + 进度条 + 团队动态。

**关键决策**
- 作品进度**全部由文件状态聚合**，不存计数器（旧站存计数器，因此需要一整套补丁去修漂移）。
- 缩略图/预览图**不落列**，由 `storage_key` 派生。
- MD5 只建普通索引、不建唯一约束：同一份字节在修订链里重传是合法操作，硬约束会把合法操作变成 500。

**验收**：登录即见「我参与的作品」，卡上能直达下一步；73 项断言通过。

### M3 翻校 ✅

**目标**：让组内日常最依赖的环节**可生产使用**。

**交付**
- 标号（归一化坐标 + 多边形 + 排版样式）；译文与校对。
- 显式状态机（9 个内部状态 → 对外五档）；状态流水。
- 署名台账（取代旧站的自由文本串）。
- 下游通知与「待办」。
- 翻校工作台：画布 + 标号列表 + 译文输入。
- 图片跨作品移动（标号随图、译文按目标语言重映射）。
- `packages/shared`：禁则换行、竖排与纵中横、字号收缩、标点检查。

**关键决策**
- **译文保留「多候选」结构**（一标号 × 一语言可有多份候选 + 选中态 + 校对态）。压平成「一标号一行」会直接丢数据。
- **事实自动前进，完成必须确认**：写译文自动进「翻译中」；「已翻译」必须显式按下并校验通过。
- 状态**逐站校验**：跨级跳跃允许（短篇一次做完很常见），但沿途每一站的条件都得满足。
- 画布与将来的 PS 导出**引同一份排版实现** —— 两边各写一套必然漂移，而漂移要等用户已经在 PS 里排完版才会被发现。

**验收**：74 项断言通过；浏览器里能完成「拖框 → 输译文 → 保存 → 翻页」全流程。

### M4 图源采集 ✅

**目标**：粘一条 X / Pixiv 链接（或一个作者主页）就能把图拉进作品，不必手工下载再上传。

**交付**（已实现）
- 7 类图源：`twitter` / `twitter_user` / `bluesky` / `bluesky_user` / `pixiv` / `pixiv_user` / `external`（直链或带 `og:image` 的网页）。
- 凭据改为**多份具名配置**（而不是全站单例）：可配 X 的 `auth_token`/`ct0`、Pixiv 的 `PHPSESSID`、Bluesky 的 handle + app password、HTTP 代理。AES-256-GCM 加密落库、输出掩码、仅管理员可读写。
- **持久化导入任务**：解析完写 `import_task_items`，每张图跑完更新那一行；重启可续、可查历史，前端 1.5s 轮询。
- 团队级 MD5 去重接入导入链路：重复计入 `duplicated` 而不是报错。

**spike 的结论**（细节与证据见 `docs/m4-sourcing-spike.md`）

选 **`impit`**（方案 2）。依据不是「参数像 Chrome」，而是 JA4 的 cipher hash `8daaf6152771` 与真 Chrome 一致；方案 1（Node 原生 `fetch` / `http2`）扩展顺序与 HTTP/2 SETTINGS 帧仍是自己的，而 Cloudflare 两层都看。**不做「用哪个客户端」的开关** —— 单一入口指纹才不会在某条支路上退化。

**计划外的坑（都是实测撞出来的）**

1. **内网出口到 Pixiv / X / 图床的直连不通**：那几个域名的 DNS 应答被污染成无关地址（`www.pixiv.net` 与 `www.google.com` 解析到同一个第三方网段）。所以 `SOURCING_PROXY` 不是可选项。它属于内网拓扑，**只写在各部署机的 `deploy/.env`**，不进仓库。
2. **同类原生模块风险要逐个验**：`impit` 也是原生模块，而测试机 CPU 没有 x86-64-v2（见 README 的 sharp 一节）。已实测 `impit-linux-x64-gnu` 在该 CPU 上正常加载。
3. **两个上游通道已经没了**：X 的 `og:image` 兜底与 `guest/activate` 现在都取不到。因此按用户抓取要求配 `bearer` + `userMediaQueryId`，缺任一项就**直接报「要配什么」**，不做无效重试。
4. **403 不等于被墙**：`i.pximg.net` 少带 `Referer` 也是 403。失败分类必须看证据（Cloudflare 挑战页特征）才判 `BLOCKED`，否则用户会被指向完全错误的方向。
5. **代理挂了与目标不可达在连接层分不开**：`impit` 两种情况都抛 `ConnectError` 而非 `Proxy*`，所以配了代理时连接失败一律归 `PROXY`。

**验收结果**：粘一条 Pixiv / X 链接即可入库；按用户批量抓取能在重启后继续；重复的图计入 `duplicated`；导入被中断后重跑**只补失败的、且不清零已有计数**。

**风险**：上游通道都是非官方接口，随时可能失效。缓解：抓取层做成可替换的 source 解析器（`sourcing/registry.ts` 一处注册），加失败分类告警，保留代理与凭据配置位。

### M5 导出与成品 ⬜

**目标**：打通「离线 PS 嵌字」闭环 —— 这是本方案与纯在线平台最不同的地方。

**交付**
- **导出**：
  - LabelPlus txt（与 PS 脚本配对，仅导出已打点标号、中心点坐标、4 位小数、BOM、CRLF）；
  - 分层 PSD（文本图层用原生 TypeTool，而不是栅格化）；
  - 工程包（原图 + 标号 + 译文，JSON / CSV / LP / ZIP）；
  - 成品打包（PNG）。
- **PS 侧脚本**：`LabelPlus_Ps_Script.jsx` —— 离线嵌字流程的关键交付物，没有它导出包在 PS 里没用。
- **成品回传**：`outputs` 表（文件多版本）→ 回传后状态推进到 `typeset` 才解锁。
- 导出体积上限与流式打包（避免一次性把几百 MB 读进内存）。

**关键决策**
- 导出必须用 `packages/shared` 里的同一份排版实现，否则「画布上看到的三行」与「导出后 PS 里的两行」会对不上。
- 现有部署里 `typeset` 被前置条件挡着（需要成品），M5 建表后放开 —— 这是有意的：与其让状态机假装走得通，不如在正确的时机说清楚。

**验收**：导出的包在 PS 里跑脚本能直接得到带译文的工程；回传成品后状态推进正确。

### M6 发布 ⬜

**目标**：一键导出发布包 → 生成草稿 → 人工确认或定时发布。

**交付**
- 平台适配层接口（`verifyCredential` / `uploadImage` / `searchTopic` / `searchMention` / `publish`）。**v1 只实现 B 站**，其他平台留接口。
- 发布队列放在 **PostgreSQL**：原子认领（`FOR UPDATE SKIP LOCKED`）+ **幂等键** + **租约**。
- 发布账号归团队（团队可持有一个或多个发布号）；**仅管理员可安排发布日程**。
- 从署名台账聚合工作人员名单 → 套用署名模板 → 生成草稿；@ 提及必须在保存时与**发布时兜底**各生成一次（覆盖重试与历史数据），否则 @ 不可点击。
- 账号 Cookie 定期校验，状态翻转写运行日志。

**要修掉的三个已知缺陷**（来自旧实现）
1. 调度器非原子认领 → 并发下重复发布；
2. 无幂等键 → 发布成功但未落库会重发；
3. 单进程标志位 → 多实例会重复发布。

**诚实说明一个消除不了的窗口**
B 站的发布接口**没有幂等参数**，所以「HTTP 返回 200 之后、写库之前崩掉」这一毫秒级窗口无法靠幂等键消除。做法是两阶段标记：调用前先写「发布中」，worker 重启时凡遇「发布中」的任务标记为**待人工确认**，绝不静默重发。代价是极端情况下需要人工点一下，换来的是不会产生重复动态。

**调度器只能在 worker 容器里跑**，backend 绝不能起调度循环 —— 否则两个容器同时发布。

**验收**：对测试账号做一次真实发布，验证 @ 可点击、署名行、话题与图片顺序；重复发布用例须证明不会产生重复动态。

### M7 迁移 ⬜

**目标**：现有彩翻的用户与数据无损搬到新站。

**交付**
- 迁移工具：**可续跑、幂等、可验证**。
- 无损验证报告：迁移前后逐表计数 + 指纹比对（对排序后的 id/key 列表取 md5），差异非零即失败。
- 测试机演练：先对生产数据的副本跑通，再谈正式切换。

**关键做法**
- **ID 用确定性 uuidv5**（由来源系统的 ObjectId 派生），于是重跑迁移天然幂等、可续跑，不依赖映射表的正确性。
- 图片按 md5 去重后搬字节；`md5` 保留以延续团队级去重语义。
- **署名台账的插入顺序必须还原原 token 顺序** —— 顺序即显示顺序，迁移报告里要有「台账回拼 == 原字符串」的断言兜住。
- 计数器**不迁**：原值是漂移的，照搬会污染新库，改为按需聚合。

**已知的有损点（要写进报告，不能藏）**
- 旧站的标号只有中心点坐标 + 多边形顶点、**没有宽高**，需要从顶点推包围盒合成；无多边形的会置 0。
- 旧凭据（明文 Cookie / session token）**一律不迁**，运维时在新系统加密重新录入。因此「无损」的边界是**领域数据 + 图片 + 署名台账**，不含密钥。

**验收**：迁移后逐表计数与指纹一致；旧凭据不在新库中；迁移报告里每个有损点都有人确认过。

---

### M8 AI 机翻 ⬜

**目标**：把「大量重复劳动」压掉一部分 —— 只做机翻，不做 AI 去字修图。

**交付**
- OCR（可选本机 sidecar）→ 自动生成标号 → 大模型翻译 → 回填为**候选译文**（默认不直接覆盖人工译文）。
- 按用户配置的多 provider（OpenAI 兼容）、密钥掩码。
- 命中术语表时优先使用术语（术语库随之落地）。

**关键决策**
- 机翻结果**只出提案，不落库为最终稿**：它进 `translations` 的候选位，由人挑。这样「AI 帮了多少忙」是可度量的，也随时能退回人工。
- 术语库（权限码早已预留）在这一步才真正需要，随 M8 落地。

**验收**：一键机翻能把一页的标号与候选译文批量填出来，人工只需挑选与修正。

## 四、上线前检查单（v1）

按顺序做，前一项不通过不进下一项：

1. **功能冻结** —— M8 之后不再加功能，只修 bug。
2. **M7 迁移在测试环境完整演练一遍**，产出无损验证报告。
3. **备份策略落地**：数据库定时 `pg_dump` 到宿主机；图片按 **md5 清单**做增量同步（图库只增，全量备份不划算）。迁移执行前必须先取一次完整快照。
4. **容量与性能**：按参照规模核对数据库参数、图片库体积余量、单张导出与打包的耗时上限。
5. **安全复查**：凭据加密落库、输出掩码、**任何密钥不进 git、不打日志**；确认 `.env` 与数据目录都被 git 忽略。
6. **部署到生产环境**：容器编排与非容器化反代只**增加**配置，不改动同机上其他服务的 nginx/cron/数据卷；改动前 `nginx -t`，改动后复验其他服务的容器存活时间未变。
7. **域名与 TLS**：生产必须 HTTPS（会话 Cookie 带 `Secure`，纯 HTTP 下登录不上）。
8. **回滚预案**：镜像保留上一个可用 tag；数据回滚靠第 3 步的快照。
9. **灰度**：先让少数人用新站做真实的一部作品，再全量切换。

## 五、明确不在 v1 范围内

写下来是为了避免后期反复讨论：

- **在线嵌字编辑器**（含笔刷、去字、液化）—— v1 走离线 PS 流程。
- **微博 / X 发布适配器** —— 只留接口。
- **AI 去字修图** —— 只做机翻。
- **R2 / remote-HTTP 存储驱动** —— 存储抽象在 M2 就按接口写好了，加驱动时只增实现不改调用点。
- **移动端适配优化** —— 能看进度即可，不做专门优化。

## 六、依赖与关键路径

```
M0 ──► M1 ──► M2 ──► M3 ────────► M5 ──► M6 ──► v1
                      │            ▲
                      └──► M4 ─────┘
                                   
M7 ──（依赖 M1–M6 的数据模型稳定）──► 上线
M8 ──（独立，可在 M6 之后并行）────► 上线
```

- **关键路径**：M3 → M5 → M6。卡住任何一个，v1 就往后推。
- **可并行**：M4（图源）与 M5（导出）互不依赖，谁先谁后都行。
- **必须最后做**：M7 迁移 —— 数据模型再动的可能性越小越好。
- M8 与 M6 可以并行，但它不是上线的阻塞项。

## 七、风险登记

| 风险 | 影响 | 缓解 | 状态 |
|---|---|---|---|
| 上游抓取通道是非官方接口，随时可能失效 | 图源采集不可用 | 抓取层做成可替换的 source 解析器；失败分类告警；保留代理与凭据配置位 | **已发生**：X 的 `og:image` 与 `guest/activate` 已失效，见 M4 一节 |
| Node 侧缺少浏览器指纹伪装能力 | 被 Cloudflare 拦的图源抓不到 | M4 开工先 spike；三级方案（纯 Node → Rust 客户端 → sidecar） | **已解决**：选 `impit`（JA4 与真 Chrome 一致），未用上 sidecar |
| 迁移的「无损」是硬承诺，但存在无法自动还原的边界 | 数据丢失 | 迁移前先做**只读盘点**，列出不可自动映射项人工定夺；迁移报告必须写明每个有损点 | 待 M7 |
| 发布接口无幂等参数，存在毫秒级崩溃窗口 | 极端情况下重复动态 | 两阶段标记 + 待人工确认；**宁可不发也不重发** | 设计已定 |
| 跨容器一致性：调度器只能在一个容器里跑 | 重复发布 | 代码入口隔离 + 队列原子认领 + 租约，双重保证 | 设计已定 |
| 导出包体积大（数百 MB） | 打包超时 / 内存爆 | 流式打包；若走 CDN 代理，大导出考虑直连源站 | 待 M5 |
| 软删除的引用计数口径不清 | 成品变孤儿 | 删除与迁移都要明确引用计数口径 | 待 M5 |
