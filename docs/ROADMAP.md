# 405nm 路线图（M1 → v1 上线）

## 一、v1 的验收标准

**一条完整链路端到端跑通**：

```
图源入库 → 翻译 → 校对 → 导出嵌字包 → PS 嵌字 → 回传成品 → 一键导出发布包 → 定时发到 B 站
```

不是「每个模块都能用」，而是**这条链路上的每一环都不需要人工搬数据**（不靠下载文件、改文件名、手动传图）。任何一环需要有人「手工补一下」，都算没打通。

配套要求：
- 现有彩翻的用户能无损迁移过来（含图片与署名），且**迁移可重跑、可验证**。
- 与既有生产环境并存部署，不触碰同机上的其他服务。
- 组内日常最依赖的环节（翻校）在 v1 就必须是**可生产使用**的，不是演示级。

## 三、逐里程碑详情

### M1 身份与团队 ✅

**目标**：所有后续功能都挂在这套身份与权限上，所以它必须先立稳。

**交付**
- 用户、团队、团队成员；邀请码绑团注册（一码绑一团队、多用途、可停用、自动入团）。
- 角色与权限：权限码落**关联表**（而非位掩码），可查询可审计；团队角色 5 个（创建人/管理员/资深/成员/见习）。
- 站点后台：用户管理、团队概览、站点设置、公告。
- 权限分两层：**团队级**与**作品级**各走各的校验。

**关键决策**
- 会话用**数据库不透明令牌**而不是 JWT —— 改密码 / 移出团队必须能立即失效，JWT 做不到。
- 密码 scrypt；登录失败次数限流（成功即清零）；注册按 IP + 全站双窗口限流。
- 权限码用点分字符串并**保留与旧站枚举码的对应关系**，供迁移时逐一映射而不是猜。

**验收**：能建团队、发邀请码、按角色看到不同入口；40 项断言通过。

### M2 项目与文件 ✅

**目标**：把「作品」这个概念立起来 —— 之后翻校、图源、导出才有挂靠的地方。

**交付**
- 作品集 / 作品 / 文件 / 目标语言；作品内角色（建作品时从团队模板实例化）。
- 作品编号（团队内自增，`UPDATE ... RETURNING` 原子分配）。
- 存储抽象（v1 只 local 驱动）；缩略图 520px / 预览图 2000px。
- **媒体字节流服务**：图片经应用鉴权后流式吐出，不放 nginx 静态目录。
- 团队级 MD5 去重；自然排序键（数字段左补零到 12 位，数据库排序即自然序）。
- Comiku 风格工作台：作品卡 + 状态 chips + 进度条 + 团队动态。

**关键决策**
- 作品进度**全部由文件状态聚合**，不存计数器（旧站存计数器，因此需要一整套补丁去修漂移）。
- 缩略图/预览图**不落列**，由 `storage_key` 派生。
- MD5 只建普通索引、不建唯一约束：同一份字节在修订链里重传是合法操作，硬约束会把合法操作变成 500。

**验收**：登录即见「我参与的作品」，卡上能直达下一步；73 项断言通过。

### M3 翻校 ✅

**目标**：让组内日常最依赖的环节**可生产使用**。

**交付**
- 标号（归一化坐标 + 多边形 + 排版样式）；译文与校对。
- 显式状态机（9 个内部状态 → 对外五档）；状态流水。
- 署名台账（取代旧站的自由文本串）。
- 下游通知与「待办」。
- 翻校工作台：画布 + 标号列表 + 译文输入。
- 图片跨作品移动（标号随图、译文按目标语言重映射）。
- `packages/shared`：禁则换行、竖排与纵中横、字号收缩、标点检查。

**关键决策**
- **译文保留「多候选」结构**（一标号 × 一语言可有多份候选 + 选中态 + 校对态）。压平成「一标号一行」会直接丢数据。
- **事实自动前进，完成必须确认**：写译文自动进「翻译中」；「已翻译」必须显式按下并校验通过。
- 状态**逐站校验**：跨级跳跃允许（短篇一次做完很常见），但沿途每一站的条件都得满足。
- 画布与将来的 PS 导出**引同一份排版实现** —— 两边各写一套必然漂移，而漂移要等用户已经在 PS 里排完版才会被发现。

**验收**：74 项断言通过；浏览器里能完成「拖框 → 输译文 → 保存 → 翻页」全流程。

### M4 图源采集 ✅

**目标**：粘一条 X / Pixiv 链接（或一个作者主页）就能把图拉进作品，不必手工下载再上传。

**交付**（已实现）
- 7 类图源：`twitter` / `twitter_user` / `bluesky` / `bluesky_user` / `pixiv` / `pixiv_user` / `external`（直链或带 `og:image` 的网页）。
- 凭据改为**多份具名配置**（而不是全站单例）：可配 X 的 `auth_token`/`ct0`、Pixiv 的 `PHPSESSID`、Bluesky 的 handle + app password、HTTP 代理。AES-256-GCM 加密落库、输出掩码、仅管理员可读写。
- **持久化导入任务**：解析完写 `import_task_items`，每张图跑完更新那一行；重启可续、可查历史，前端 1.5s 轮询。
- 团队级 MD5 去重接入导入链路：重复计入 `duplicated` 而不是报错。

**spike 的结论**（细节与证据见 `docs/m4-sourcing-spike.md`）

选 **`impit`**（方案 2）。依据不是「参数像 Chrome」，而是 JA4 的 cipher hash `8daaf6152771` 与真 Chrome 一致；方案 1（Node 原生 `fetch` / `http2`）扩展顺序与 HTTP/2 SETTINGS 帧仍是自己的，而 Cloudflare 两层都看。**不做「用哪个客户端」的开关** —— 单一入口指纹才不会在某条支路上退化。

**计划外的坑（都是实测撞出来的）**

1. **内网出口到 Pixiv / X / 图床的直连不通**：那几个域名的 DNS 应答被污染成无关地址（`www.pixiv.net` 与 `www.google.com` 解析到同一个第三方网段）。所以 `SOURCING_PROXY` 不是可选项。它属于内网拓扑，**只写在各部署机的 `deploy/.env`**，不进仓库。
2. **同类原生模块风险要逐个验**：`impit` 也是原生模块，而测试机 CPU 没有 x86-64-v2（见 README 的 sharp 一节）。已实测 `impit-linux-x64-gnu` 在该 CPU 上正常加载。
3. **两个上游通道已经没了**：X 的 `og:image` 兜底与 `guest/activate` 现在都取不到。因此按用户抓取要求配 `bearer` + `userMediaQueryId`，缺任一项就**直接报「要配什么」**，不做无效重试。
4. **403 不等于被墙**：`i.pximg.net` 少带 `Referer` 也是 403。失败分类必须看证据（Cloudflare 挑战页特征）才判 `BLOCKED`，否则用户会被指向完全错误的方向。
5. **代理挂了与目标不可达在连接层分不开**：`impit` 两种情况都抛 `ConnectError` 而非 `Proxy*`，所以配了代理时连接失败一律归 `PROXY`。

**验收结果**：粘一条 Pixiv / X 链接即可入库；按用户批量抓取能在重启后继续；重复的图计入 `duplicated`；导入被中断后重跑**只补失败的、且不清零已有计数**。

**风险**：上游通道都是非官方接口，随时可能失效。缓解：抓取层做成可替换的 source 解析器（`sourcing/registry.ts` 一处注册），加失败分类告警，保留代理与凭据配置位。

### M5 导出与成品 ✅

**目标**：打通「离线 PS 嵌字」闭环 —— 这是本方案与纯在线平台最不同的地方。

**交付**
- **导出**：
  - LabelPlus txt（与 PS 脚本配对，仅导出已打点标号、中心点坐标、4 位小数、BOM、CRLF）；
  - ~~分层 PSD（文本图层用原生 TypeTool，而不是栅格化）~~ —— **后改为不做**，理由见下方差异表；
  - 工程包（原图 + 标号 + 译文，JSON / CSV / LP / ZIP）；
  - 成品打包（PNG）。
- **PS 侧脚本**：`LabelPlus_Ps_Script.jsx` —— 离线嵌字流程的关键交付物，没有它导出包在 PS 里没用。
- **成品回传**：`outputs` 表（文件多版本）→ 回传后状态推进到 `typeset` 才解锁。
- 导出体积上限与流式打包（避免一次性把几百 MB 读进内存）。

**关键决策**
- 导出必须用 `packages/shared` 里的同一份排版实现，否则「画布上看到的三行」与「导出后 PS 里的两行」会对不上。
- 现有部署里 `typeset` 被前置条件挡着（需要成品），M5 建表后放开 —— 这是有意的：与其让状态机假装走得通，不如在正确的时机说清楚。

**实际交付（与原计划的差异）**

| 原计划 | 实际 | 说明 |
|---|---|---|
| LabelPlus txt | ✅ | 格式对着官方 PS 脚本的解析器反推，见 README「不要随手改」一节 |
| 工程包（JSON/CSV/LP/ZIP） | ✅ | ZIP + 内嵌 txt + `manifest.json` + `说明.txt`。CSV 没做 —— 没人要过，加它只是多一种会过期的格式 |
| 成品打包（PNG） | ✅ | 按语言打包，每张取最新版本 |
| **分层 PSD** | ⛔ **明确不做** | 导出就两样：**原图 + LabelPlus 兼容 txt**。PSD 由 PS 自己另存即可；服务端生成要引入 libvips 吐裸 RGBA 这条没必要的依赖链。不要在导出里再加第三种格式 |
| PS 侧脚本随包分发 | ❌ 未随包 | LabelPlus 官方脚本是 **GPLv2**，而本仓库是公开仓库且没有 LICENSE。是否收进第三方 GPL 代码是仓库所有者的决定，不该替他做。改为在 `说明.txt` 与导出弹窗里给出获取方式与安装步骤 |

**开工时没预料到的两处**

1. **`outputCountFor()` 是个恒返回 0 的桩**（M3 留的，注释写着「M5 建表后改成一次 count 即可」）。
   建表时忘了接线，后果是**「已嵌字」在生产环境里永远走不到**，而报错还说
   「该图片还没有回传成品」—— 明明刚传过。是 m5-verify 的断言把它逼出来的。
2. **一句过期的版本说明变成了谎话**：`file-state.ts` 里为 typeset 失败附的
   「（成品回传是 M5 的嵌字环节，当前版本尚未开放）」，在 M5 做完之后就是在骗人。
   m3-verify 里原本还把这句话钉成了断言 —— 两处都改了。

**验收**：m5-verify 79 项断言通过；导出的包在 PS 里跑官方脚本能直接得到带译文的工程；
回传成品后状态能推进到 `typeset`（文件级）与 `publishable`（作品级）。

### M6 发布 ✅

**目标**：一键导出发布包 → 生成草稿 → 人工确认或定时发布。

**交付**
- 平台适配层接口（`verifyCredential` / `uploadImage` / `searchTopic` / `searchMention` / `publish`）。**v1 只实现 B 站**，其他平台留接口。
- 发布队列放在 **PostgreSQL**：原子认领（`FOR UPDATE SKIP LOCKED`）+ **幂等键** + **租约**。
- 发布账号归团队（团队可持有一个或多个发布号）；**仅管理员可安排发布日程**。
- 从署名台账聚合工作人员名单 → 套用署名模板 → 生成草稿；@ 提及必须在保存时与**发布时兜底**各生成一次（覆盖重试与历史数据），否则 @ 不可点击。
- 账号 Cookie 定期校验，状态翻转写运行日志。

**要修掉的三个已知缺陷**（来自旧实现）
1. 调度器非原子认领 → 并发下重复发布；
2. 无幂等键 → 发布成功但未落库会重发；
3. 单进程标志位 → 多实例会重复发布。

**诚实说明一个消除不了的窗口**
B 站的发布接口**没有幂等参数**，所以「HTTP 返回 200 之后、写库之前崩掉」这一毫秒级窗口无法靠幂等键消除。做法是两阶段标记：调用前先写「发布中」，worker 重启时凡遇「发布中」的任务标记为**待人工确认**，绝不静默重发。代价是极端情况下需要人工点一下，换来的是不会产生重复动态。

**调度器只能在 worker 容器里跑**，backend 绝不能起调度循环 —— 否则两个容器同时发布。

**实际交付**

| 计划 | 实际 |
|---|---|
| 平台适配层 + B 站适配器 | ✅ 搬 380nm 的 `bilibili.js`（自有仓库），三处刻意改动：`upload_id` 由任务派生（确定性）、失败按「有没有副作用」分类、出网**不走抓取那层的代理与指纹** |
| Postgres 队列（原子认领 + 幂等键 + 租约） | ✅ 三个缺陷全修，另加**两阶段标记** |
| 账号库与署名模板 | ✅ `credit_directory` + `publish_templates`；署名从 `file_credits` **台账**聚合，不再解析自由文本串 |
| 一键发布包 → 草稿 → 定时发布 | ✅ 作品页生成草稿（图片在这步快照），团队页管账号与队列 |
| 账号 Cookie 定期校验 | ✅ worker 里单开一条低频线，状态翻转时才记日志 |

**为什么发布不走 `SOURCING_PROXY`**：那一层是为被反爬拦的图源准备的（浏览器指纹 +
必经代理）。B 站是国内站点，2026-09-29 实测测试机直连 `api.bilibili.com`
HTTP 200 / 0.2s，而同机 `pixiv.net` 完全不通。这里做的是**带 Cookie 的身份化
API 调用**，既不需要伪装浏览器，也不该被绕到境外代理上去。

**开工时没预料到的两处**

1. **`recoverStalled` 里的 `= ANY(${ids})` 在 postgres.js 下是坏的**：
   数组被绑成单个参数，`ANY` 收到字符串会当数组字面量解析、报
   `malformed array literal`。调用处裹在 try/catch 里，症状是
   **「不确定发没发出去就交人工」这道安全网从来没生效过**，只是每 3 秒
   往日志里刷一条错误。改用 `inArray`。
2. **不传 `targetId` 时语言默认成空串**：成品是按项目语言码存的，于是一条都
   查不到，报「还没有可发布的成品图」—— 明明刚传完。语言解析收口到
   `publish/compose.ts` 的 `resolveLanguage`，成品路由与发布草稿共用一份。

**验收**

- ✅ `m6-verify` 62 项断言（连跑三轮稳定）。队列语义那部分**直接调队列函数**
  而不是走 HTTP —— 「两阶段标记」「租约回收」「needs_review」的价值恰恰在于
  「进程在中间死掉」时会发生什么，那件事没法用 HTTP 触发。
- ✅ 全套 7 个套件 486 项断言零失败；邻居容器 uptime 未变。
- ⬜ **真实发布尚未做**：自动化脚本刻意不碰（发出去的动态收不回来）。
  需要人工对测试账号做一次，验 @ 可点击、署名行、话题、图片顺序，
  以及「同一条草稿重复入队不产生重复动态」。**不要用生产账号做这件事。**

### M7 迁移 ✅

**目标**：现有彩翻的用户与数据无损搬到新站。

**交付**（操作手册见 `docs/m7-migration.md`）
- `deploy/moeflow-export.sh`：只读导出旧库快照（凭据在容器内展开，脚本里没有账号密码）。
- `backend/src/cli/migrate-moeflow.ts` 三个子命令：`inventory`（只算不写）/ `migrate`（写库 + 就地核验）/ `verify`（只核验）。
- 无损验证报告 `migrate-report.json`：**逐行逐字段比对** + 图片字节摘要复算 + 行数复查 + 导出快照自检；
  另有有损点清单、**每个旧集合的去向**、逐表计数。退出码非零即失败。
- 真机演练：旧站测试实例（4 用户 / 1 团队 / 1 作品 / 36 图 / 14 标号 / 14 译文）全量迁入独立库，两遍迁移幂等、核验全绿。

**关键做法**
- **ID 用确定性 uuidv5**（由旧库 ObjectId 派生），重跑天然幂等、可续跑，不依赖映射表；写库统一 `onConflictDoNothing`，只增不改。
- **标号与译文是流式归并的**：`source.json` 按 `_id`、`translation.json` 按 `{o:1,t:1}` 升序，两边流式读、按标号归并，内存里只留一个组 —— 上百万行也迁得动。顺序不对**直接报错退出**，不静默错配。
- **核验与迁移共用同一份计划与同一批纯函数**：核验不是「自己跟自己比」，而是用同一套映射重算期望值再与库里的行比。演练里它当场抓出了两个真问题（见下）。
- **署名台账按旧站 token 顺序逐行插入**：顺序即显示顺序，核验里有专门一条按 `seq` 的顺序比对。
- 图片：字节按确定性键落盘，摘要与旧库 `md` 交叉核对；取不到字节的行照样建（空记录，界面显示占位图），
  且**区分「旧站本来就没有」与「我们取不到」** —— 前者是既成事实，后者是配置有问题，混成一类会掩盖真问题。
- 计数器与旧凭据**不迁**；旧凭据（Cookie / session / app password）一律不进新库。

**演练中真被抓住的两个问题**（都是「看起来对、其实错」的那一类）
1. 旧站的权限码分两段：`1010+` 是各域自定义的，`1/5/10/15/20/101-120` 是**两个域共用的基类**。
   起初只映射了前一段，于是作品角色上的 `5/10/105` 落成了「本站不存在的权限」，
   而 `project.edit / project.delete / project.member.manage` 又被当成「本站新权限」**补发给了所有系统角色**
   —— 翻译、校对会凭空拿到成员管理权。修法是给这三条补上 `legacyCode`，并补一张「一个本站码对应多个旧码」的表。
2. 行数复查按 `legacy_id IS NOT NULL` 数 `roles`，但项目角色模板的 `legacy_id` 是空的（按本站默认补建），
   于是「库里 5 行 vs 期望 12 行」永远对不上。修法是给复查加上作用域限定。

**已知的有损点（报告里逐类列出，`confirm` 的需人工确认）**
- 标号只有中心点 + 多边形顶点、**没有宽高**，`w/h` 由多边形包围盒合成；无多边形的记 0（是「没有框」，不是「框在左上角」）。
- 旧站允许一份译文都不选（导出时另按一套顺序兜底），本站只认「选中」→ 迁移时按旧站挑法**把最佳候选落成选中**。
- 团队/作品「允许任何人申请加入」、标签、术语库、个人签名、头像、OCR 配额等本站没有的能力：不迁（各有明确去向与理由）。

**验收**：逐表逐字段核对零差异、图片字节摘要全部对得上、两遍迁移幂等、核验在数据被改动时**确实会失败**；
演练通过后仍需为**正式切换**另约窗口（工具已就绪，数据切换是运维动作）。

### M8 AI 机翻 ✅

**目标**：把「大量重复劳动」压掉一部分 —— 只做机翻，不做 AI 去字修图。

**交付**
- **自动标号**：视觉模型读一页，直接给出「文字块位置 + 原文」；与已有标号按中心点距离去重，一页最多接收 `AI_MAX_MARKERS` 条。
- **机翻**：把一页的标号原文批量译成目标语言，命中术语的必须用术语的译法。
- **术语库**（团队资产）：建库、粘贴批量导入、按语言隔离、关键词搜索；机翻时命中子串的词自动带上（长词优先、封顶 `AI_GLOSSARY_LIMIT` 条）。
- **按用户配置的模型接入**：OpenAI 兼容（官方 / Azure / 自建 one-api / vLLM 都行），每人一份、Key 加密存储且只回掩码，可指定识图模型与对话模型、可单独设出口。
- API：`/ai/providers*`、`/files/:id/ai/markers/{propose,}`、`/files/:id/ai/translations/{propose,}`、`/teams/:id/term-banks`、`/term-banks/:id/terms`。

**关键决策（都是「宁可不省事，也不要出错」那一类）**
- **只出提案，不落库**：`propose` 与 `apply` 是两次独立请求，中间必须有人看一眼。
  机翻写进去的是**候选位**（`machineTranslated = true`、**不选中**），人工自己写过、已选中、已校对的行**一律不动** —— 判断依据是行自己的状态，所以换个人来跑也不会踩到别人的稿子。
- **识别与翻译共用一次「提案 → 复核 → 应用」的交互**，没有「一键静默写入」。
- **不做本机 OCR sidecar**：那条路要装 tesseract / paddle 之类的东西，而模型的看图能力已经够用；一页一次调用，比「先检测框、再逐框裁剪识别」省掉几十次往返。要更准就换更大的模型。
- **送预览变体而不是原图**：模型自己也会缩图，传几千像素的原图只是白花流量；归一化按**实际送出去的那张图**的尺寸算。
- 权限复用已有的码：团队域 `quota.ocr` / `quota.mt`（能不能用额度），项目域 `label.add` / `tra.add`（能不能往这个作品里写）。
  术语库用 `term_bank.*` / `term.*` —— 迁移时这些码已经挂在各团队角色上了，所以**不用重新配权限**。

**验收**：工作台点「AI」→ 生成提案 → 表格里改一改、勾掉不要的 → 应用；标号落位、机翻进候选位、人工稿不被覆盖。
`tests/m8-verify.mjs` 67 项断言，模型调用全部走脚本内置的假服务（不碰外网）。

## 四、上线前检查单（v1）

按顺序做，前一项不通过不进下一项：

1. **功能冻结** —— M8 之后不再加功能，只修 bug。
2. **M7 迁移在测试环境完整演练一遍**，产出无损验证报告。
3. **备份策略落地**：数据库定时 `pg_dump` 到宿主机；图片按 **md5 清单**做增量同步（图库只增，全量备份不划算）。迁移执行前必须先取一次完整快照。
4. **容量与性能**：按参照规模核对数据库参数、图片库体积余量、单张导出与打包的耗时上限。
5. **安全复查**：凭据加密落库、输出掩码、**任何密钥不进 git、不打日志**；确认 `.env` 与数据目录都被 git 忽略。
6. **部署到生产环境**：容器编排与非容器化反代只**增加**配置，不改动同机上其他服务的 nginx/cron/数据卷；改动前 `nginx -t`，改动后复验其他服务的容器存活时间未变。
7. **域名与 TLS**：生产必须 HTTPS（会话 Cookie 带 `Secure`，纯 HTTP 下登录不上）。
8. **回滚预案**：镜像保留上一个可用 tag；数据回滚靠第 3 步的快照。
9. **灰度**：先让少数人用新站做真实的一部作品，再全量切换。

## 五、明确不在 v1 范围内

写下来是为了避免后期反复讨论：

- **在线嵌字编辑器**（含笔刷、去字、液化）—— v1 走离线 PS 流程。
- **分层 PSD 导出** —— 导出只做「原图 + LabelPlus 兼容 txt」，PSD 由 PS 另存。
- **微博 / X 发布适配器** —— 只留接口。
- **AI 去字修图** —— 只做机翻。
- **R2 / remote-HTTP 存储驱动** —— 存储抽象在 M2 就按接口写好了，加驱动时只增实现不改调用点。
- **移动端适配优化** —— 能看进度即可，不做专门优化。

## 六、依赖与关键路径

```
M0 ──► M1 ──► M2 ──► M3 ────────► M5 ──► M6 ──► v1
                      │            ▲
                      └──► M4 ─────┘
```

- **可并行**：M4（图源）与 M5（导出）互不依赖，谁先谁后都行。
- **必须最后做**：M7 迁移 —— 数据模型再动的可能性越小越好。
- M8 与 M6 可以并行，但它不是上线的阻塞项。

## 七、风险登记

| 风险 | 影响 | 缓解 | 状态 |
|---|---|---|---|
| 上游抓取通道是非官方接口，随时可能失效 | 图源采集不可用 | 抓取层做成可替换的 source 解析器；失败分类告警；保留代理与凭据配置位 | **已发生**：X 的 `og:image` 与 `guest/activate` 已失效，见 M4 一节 |
| Node 侧缺少浏览器指纹伪装能力 | 被 Cloudflare 拦的图源抓不到 | M4 开工先 spike；三级方案（纯 Node → Rust 客户端 → sidecar） | **已解决**：选 `impit`（JA4 与真 Chrome 一致），未用上 sidecar |
| 迁移的「无损」是硬承诺，但存在无法自动还原的边界 | 数据丢失 | 迁移前先做**只读盘点**，列出不可自动映射项人工定夺；迁移报告必须写明每个有损点 | 待 M7 |
| 发布接口无幂等参数，存在毫秒级崩溃窗口 | 极端情况下重复动态 | 两阶段标记 + 待人工确认；**宁可不发也不重发** | 设计已定 |
| 跨容器一致性：调度器只能在一个容器里跑 | 重复发布 | 代码入口隔离 + 队列原子认领 + 租约，双重保证 | 设计已定 |
| 导出包体积大（数百 MB） | 打包超时 / 内存爆 | 流式打包；若走 CDN 代理，大导出考虑直连源站 | 待 M5 |
| 软删除的引用计数口径不清 | 成品变孤儿 | 删除与迁移都要明确引用计数口径 | 待 M5 |
